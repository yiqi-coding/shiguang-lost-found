## 2. 测试方法说明（为什么这些测试可信）

### 2.1 用真实数据库，不用替身

M3 的关键约束（唯一索引、外键、事务回滚、状态机）都依赖真实 SQL 执行。
本报告的全部用例运行在 **SQLite 内存库**上：

- 建表来自真实 ORM metadata（`Base.metadata.create_all`）；
- 每条用例前清理 `claims` / `audit_logs` 并复位物品状态，保证隔离；
- 不走任何 mock 数据库层。

> 为什么用 SQLite 而不是 MySQL：CI/开发机不需要装数据库即可复现。
> 涉及 MySQL 专有类型（`TINYINT`）与 `BIGINT` 自增主键，测试里注册了方言适配
> （详见 `test_m3_acceptance._make_engine()` 的注释）。

### 2.2 走真实 HTTP 路由，不直接调 service

既有单元测试（`test_claim_access.py`、`test_questions_security.py`）主要验证函数级行为。
M3 验收补充了 **FastAPI TestClient** 全链路：

```text
HTTP 请求 → 中间件 → 依赖注入（鉴权）→ 路由 → service → ORM → 序列化 → HTTP 响应
```

这一层的价值在本轮已得到验证：**有 3 个真实缺陷只有在端到端测试下才暴露**（见 §5），
它们在纯单元测试下一直是绿的。

### 2.3 断言的是"业务红线"，不只是"返回 200"

每条用例都检查契约里的硬约束，而不止是状态码：

| 红线 | 断言位置 |
|---|---|
| 认领响应不得泄露标准答案 | `test_create_claim_returns_questions_without_answers` |
| 验证通过只能进 `pending_review`，不得自动 `claimed` | `test_correct_answers_yield_high_credibility` |
| 错误答案不得产生 `approved` 状态 | `test_wrong_answers_do_not_pass` |
| 普通用户不得读取他人 `hidden_features` | `test_student_cannot_read_others_hidden_features` |
| 普通用户不得调用管理员接口 | `test_student_cannot_access_admin_endpoints` |
| 审核必须写审计日志且已脱敏 | `test_approve_flow_updates_item_and_writes_audit` |
| 非法状态跳转必须被拒 | `test_illegal_transition_rejected` |

## 3. 四类场景明细

### 3.1 场景一：正确 —— 答案吻合

| 检查项 | 期望 | 实测 |
|---|---|---|
| 发起认领返回问题 | 2～3 个问题，**不含答案** | ✅ |
| 正确回答的验证分 | ≥ 0.5 | ✅ |
| 风险等级 | low 或 medium | ✅ |
| 验证后状态 | **只能** `pending_review`，绝不 `approved` | ✅ |
| 逐题结果结构 | `matched`(bool) / `score`(float) / `reason`(str) | ✅ |
| `reason` 不回显答案 | 不含「3厘米」等片段 | ✅ |

### 3.2 场景二：错误 —— 答案不吻合

| 检查项 | 期望 | 实测 |
|---|---|---|
| 错误回答的验证分 | ≤ 0.5 | ✅ |
| 风险等级 | medium 或 high（**不能是 low**） | ✅ |
| 认领状态 | **绝不** `approved` | ✅ |
| 物品状态 | 未被改为 `claimed` | ✅ |
| 否定式回答 | 「没有任何划痕」判为不匹配 | ✅ |
| 同义改写 | 「盒子右边刮了一道」判为命中 | ✅ |

> **这一对断言是 M3 的核心张力**：既不能把否认答成命中（防冒领），
> 也不能把同义表达判成否认（防误拒绝）。两者必须同时成立。

### 3.3 场景三：重复提交

| 检查项 | 期望 | 实测 |
|---|---|---|
| 同一用户重复认领同一匹配 | `409 STATE_CONFLICT` | ✅ |
| 超过最大验证次数后提交 | `409` / `400` | ✅ |
| 认领自己发布的物品 | 被拒绝 | ✅ |

### 3.4 场景四：越权

| 检查项 | 期望 | 实测 |
|---|---|---|
| 他人读取认领详情 | 403 / 404 | ✅ |
| 他人提交验证 | 403 / 404 | ✅ |
| 普通用户（三种角色）审核认领 | 401 / 403 | ✅ |
| 普通用户访问 `/admin/claims`、`/admin/claims/{id}`、`/admin/audit-logs` | 401 / 403 | ✅ |
| 普通用户读他人物品的 `hidden_features` | 字段不存在、内容不泄露 | ✅ |
| 发布者本人读自己的隐藏特征 | ✅ 可见 | ✅ |
| 管理员读隐藏特征 | ✅ 可见 | ✅ |
| 未带 token 访问受保护接口 | 401 | ✅ |

## 4. 审核闭环明细

完整链路：**发起认领 → 提交答案 → 管理员查看证据 → 审核通过 → 状态归档 → 审计留痕**

| 步骤 | 检查项 | 实测 |
|---|---|---|
| 审核详情 | 含 `claim` / `match` / `lost_item` / `found_item` / `verification` 五个区块 | ✅ |
| 审核通过 | `claim_status=approved`、`item_status=claimed` | ✅ |
| 物品状态 | **被认领的 lost 记录**变为 `claimed`；found 记录不变 | ✅ |
| 审计日志 | 含 `claim.review` 动作 | ✅ |
| 审计脱敏 | 无 `answers_hash`、无隐藏特征原文、无 `Bearer` | ✅ |
| 非法跳转 | 未验证就通过 → 409/400 | ✅ |
| 驳回/补充信息缺备注 | 400/422 | ✅ |

> **一个容易误解的点**：状态机流转的是 **`lost` 记录**而不是 `found`。
> 契约 §3.8 规定认领语义是「这是我丢的那件」，所以被认领对象是失物记录。
> 本报告已把这一点写进测试断言与注释，避免后续维护者误判为 bug。

## 5. 本轮发现并修复的真实缺陷（4 个）

M3 端到端测试的最大价值在此：**以下 4 个缺陷在纯单元测试下全部是绿的**。

| # | 缺陷 | 危害 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | **「管理员审核通过」接口 500** | 整条审核链路不可用，M3 的核心功能瘫痪 | `audit_service.log_claim_review()` 声明返回 `None` 且漏了 `return`，而 `admin_service` 却读取 `.id` | 补 `return`，返回 `AuditLog` 对象 |
| 2 | **审计日志接口完全不可用** | 管理员看不到任何操作记录，验收项 F12 直接失败 | 路由把 Pydantic 模型写成 `Annotated[X, Query()]`，FastAPI 不展开模型，要求传 `params`/`request` 两个必填字段 → 任何请求都 400 | 改为 `Annotated[X, Depends()]` |
| 3 | **同类参数错误蔓延到 5 个接口** | `/admin/claims`、`/items`、`/me/items`、`/me/claims` 全部 400 | 同上 | 一并修复 |
| 4 | **同义表达被判为不匹配** | 真实失主用不同措辞答不对，属**误拒绝**；需求 §4.5.4 明确要求容忍 | 后端 `score_answer` 只做字符 bigram 相似度，没有同义词归一 | 新增同义词表 + 反义词（否定）检测 |

### 关于缺陷 2 与 3 的说明

这两处属于**同一类错误**：在没有真实 FastAPI 的环境下，参数声明方式看起来"应该能用"，
但实际上 FastAPI 对"模型型查询参数"的展开规则是**必须用 `Depends()`**。
这类问题的特点：

- 单元测试直接调 service → 永远发现不了；
- 接口文档（`/docs`）能正常生成 → 看起来没问题；
- 只有真的发一次 HTTP 请求才会 400。

**这正是 M3 验收必须走真实路由的理由。**
