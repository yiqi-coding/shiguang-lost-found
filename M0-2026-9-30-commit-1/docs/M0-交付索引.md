## 4. 评审检查清单

### 4.1 契约完整性

- [ ] 21 个接口（含健康检查）在契约中均有请求/响应示例
- [ ] 全部错误码有 HTTP 状态码映射，且参数错误不返回 500
- [ ] 状态流转图与状态机的合法跳转集合一致
- [ ] 分页结构、`X-Request-ID`、统一响应包装在三处（契约 / 后端代码 / 前端封装）一致
- [ ] 枚举值在契约、后端 `enums.py`、前端 `types/`、数据集四处一致

### 4.2 安全红线

- [ ] 普通用户视角的物品响应不含 `hidden_features`（后端序列化唯一收口）
- [ ] 认领响应不含标准答案、答案哈希、答案原文
- [ ] 管理员操作 100% 写审计日志
- [ ] 日志过滤器覆盖 Authorization / 密钥 / 隐藏特征 / 答案
- [ ] `.env` 在 `.gitignore` 中，仓库只有 `.env.example`
- [ ] 上传校验五重（扩展名 / Content-Type / 魔数 / 大小 / 可解析性）
- [ ] 数据库账号对 `audit_logs` 无 UPDATE/DELETE 权限

### 4.3 可运行性

- [ ] 后端依赖清单完整（`backend/requirements.txt`）
- [ ] 前端依赖清单完整（`frontend/package.json`）
- [ ] 算法服务可在无真实模型的情况下运行（确定性 Mock）
- [ ] 演示数据集满足：≥60 条物品 / lost ≥30 / found ≥30 / 正样本 ≥20 / 负样本 ≥20（含 ≥8 hard negative）/ 覆盖 6 类
- [ ] 数据库可从零初始化（`scripts/init_db.sql` 或 `alembic upgrade head`）
- [ ] 三个 Dockerfile 与 `docker-compose.yml` 可构建（网络可用时验证）

### 4.4 演示可行性

- [ ] 答辩脚本 14 步在设计中均有对应页面与接口（见 [plan.md](plan.md) §9）
- [ ] 匹配页能完整展示「六维分 → 加权 → 总分」的推导过程
- [ ] 降级路径清晰：MaaS / 算法 / Redis / OBS 四类故障均有对应表现
- [ ] 演示账号与一键登录（仅非生产环境）可用

## 6. 契约变更流程

```text
发现需要变更
   → 在 docs/api-contract.md 或 docs/database-design.md 末尾「变更记录」登记一行
   → 标注：版本 / 日期 / 变更人 / 内容 / 影响范围 / 是否破坏兼容
   → 破坏性变更需三方（甲方 / 前端 / 后端）确认
   → 同步修改：后端 models+schemas+routes、前端 types+api、算法 schemas、数据集、OpenAPI
   → 更新本文件 §3「冻结内容速查」
```

**禁止**：代码先行、文档不更新；或在多个文件里各自定义同一份枚举/权重。
