# 拾光 · 算法设计说明

> 状态：**已冻结**（Baseline v1.0）
>
> 版本：Baseline v1.0 ｜ 模型版本标识：`baseline-1.0` ｜ 更新日期：2026-09-30
>
> 权威接口契约见 [api-contract.md](api-contract.md) §4；配置权威来源为 `algorithm/config/matching.yaml`。
>
> **核心原则**：**数值由程序计算，AI 只负责理解与解释。** 所有分数可复现、可解释、可配置。

## 1. 算法服务定位

算法服务是一个**独立可替换**的 HTTP 服务（默认 `http://algorithm:9000`），后端通过
`backend/app/clients/algorithm_client.py` 调用，**不依赖任何具体模型类名**。

```text
后端 (FastAPI)                         算法服务 (FastAPI)
    │                                        │
    │  1. 结构化过滤候选（DB 查询）            │
    │ ─────────────────────────────────────► │
    │  POST /algorithm/v1/match              │
    │    {query_item, candidate_items[]}     │
    │                                        │  ├─ 类别分
    │                                        │  ├─ 属性/文本分
    │                                        │  ├─ 图像相似度
    │                                        │  ├─ 时间合理度
    │                                        │  ├─ 地点合理度
    │                                        │  └─ 品牌/型号分
    │  ◄──────────────────────────────────── │
    │    {model_version, results[]}          │
    │                                        │
    │  2. 落库 matches + 写 Redis 缓存         │
    │  3. 组装可解释响应（evidence/uncertainties/risk_tips）
```

**为什么让后端做候选过滤？** 避免算法服务反向依赖业务数据库，降低耦合；算法服务只做
「给定量候选打分」这一件事，便于独立测试与替换。

## 3. 匹配评分模型

### 3.1 总分公式（冻结，需求 §4.4.2）

```text
总分 = 0.20 × 类别分
     + 0.25 × 属性/文本分
     + 0.20 × 图像相似度
     + 0.15 × 时间合理度
     + 0.15 × 地点合理度
     + 0.05 × 品牌/型号分
```

- 全部维度分与总分归一化到 `[0, 1]`；
- **权重只能从 `algorithm/config/matching.yaml` 读取**，代码中不得硬编码；
- 有单元测试断言 `total_score == Σ(权重 × 维度分)`（容差 `1e-6`）；
- `matches.weights_snapshot` 保存计算时的权重快照，**保证权重调整后历史结果仍可复现**。

### 3.2 各维度计算

#### 3.2.1 类别分

| 情形 | 分数 |
|---|---|
| 完全一致（含别名归一化，如「蓝牙耳机」→「无线耳机」） | 1.00 |
| 同族不同类（见 `families` 配置） | 0.60 |
| 声明为相关（见 `related_pairs`） | 0.25 |
| 一方为「其他」 | 0.30 |
| 不相关 | 0.00 |

> 别名表与族关系全部在 `matching.yaml > rules.category` 中配置。

#### 3.2.2 属性/文本分

三个子项融合（内部权重：字符 n-gram 0.40 / 关键词重叠 0.25 / 属性匹配 0.35）：

| 子项 | 方法 |
|---|---|
| 字符 n-gram | 中文 2-gram + 3-gram，Dice 系数 |
| 关键词重叠 | 标题与描述的关键词交集 |
| 属性匹配 | 颜色 / 材质 / 特征词表配对（权重 0.70）+ 颜色材质得分（0.30） |

融合相似度经**分段校准**映射为语义化分数，保留部分匹配含义：

| 融合相似度 | 文本分 |
|---|---|
| ≥ 0.75 | 1.00 |
| ≥ 0.55 | 0.85 |
| ≥ 0.35 | 0.65 |
| ≥ 0.15 | 0.45 |
| < 0.15 | 0.25 |

**颜色冲突**是重要的负信号：一方黑一方白 → 0.10（而非 0）。

#### 3.2.3 图像相似度

**可插拔接口设计**：

```python
class ImageEmbedder(Protocol):
    def embed(self, image_ref: str) -> list[float]: ...
```

| 实现 | 说明 | 状态 |
|---|---|---|
| `MockImageEmbedder` | 由图片 URL/类别文本经**稳定哈希**生成 64 维伪向量，再算余弦相似度 | ✅ Baseline 使用 |
| 华为云 MaaS 多模态模型 | 调用云端视觉理解接口获取向量 | ⬜ 待接入 |
| CLIP / 其他开源模型 | 本地部署 | ⬜ 可选 |

**Mock 的确定性要求**：同一输入必须产生同一输出（禁止随机数与时间戳参与），保证测试可重复运行。

**无图片时的兜底**：使用 `category + title + description` 的文本特征向量，响应中在 `uncertainties` 标注「未提供图片，图像分基于文本兜底」。

真实模型接入方式见 §8。

#### 3.2.4 时间合理度

**分段函数**（差值越小分越高），并支持「失物时间范围 vs 拾取单点时间」（取点到区间的最短距离）：

| 时间差 | 分数 | 插值方式 |
|---|---|---|
| ≤ 2 小时 | 1.00 | flat |
| 2 ~ 12 小时 | 1.00 → 0.80 | linear |
| 12 ~ 24 小时 | 0.60 | step |
| 24 ~ 72 小时 | 0.30 | step |
| > 72 小时 | 0.10 | flat |
| **时间缺失** | **0.50（可配置中性分）** | — |

**强制要求**

- 时间缺失**绝不能抛异常**，必须返回中性分并标记 `unknown`；
- 拾取时间早于丢失时间时，按绝对差计算但在 `uncertainties` 中标注「顺序异常」；
- 输入格式支持多种写法（见 `matching.yaml > rules.time.event_time_formats`），全部失败则视为 unknown。

#### 3.2.5 地点合理度

依赖**校园地点层级表**（`config/locations.yaml`），解析中文地点字符串为结构化字段：

```text
"图书馆三楼靠窗自习区"  →  {campus: "东湖校区", building: "图书馆", floor: "三楼", spot: "靠窗自习区"}
```

| 关系 | 分数 |
|---|---|
| 同一具体地点 | 1.00 |
| 同一建筑不同楼层 | 0.85 |
| 相邻建筑 | 0.60 |
| 同一校区较远地点 | 0.35 |
| 不同校区 | 0.10 |
| **未知 / 解析失败** | **0.50** |

**强制要求**

- 地点规则**必须写入配置或数据库**，不得只写死在前端；
- 解析失败不得抛异常，返回未知分；
- 虚构校园需覆盖 ≥ 2 个校区、每校区若干建筑、建筑间相邻关系。

#### 3.2.6 品牌/型号分

| 情形 | 分数 |
|---|---|
| 双方一致（含别名归一化，如 `AirPods` / `苹果` / `Apple`） | 1.00 |
| 型号部分匹配（子串关系） | 0.70 ~ 0.75 |
| 一方缺失 | 0.50（中性，并产出 `uncertainties`） |
| 双方均缺失 | 0.50 |
| 明确冲突 | 0.05 ~ 0.15 |

> **品牌冲突是强负信号**：同为黑色耳机但一方 Apple 一方华为，不应因为颜色与类别相同就得高分。

### 3.3 匹配等级与展示阈值

| 等级 | 总分区间 | 展示 |
|---|---|---|
| `high` | ≥ 0.75 | 「高匹配」 |
| `medium` | 0.50 ~ 0.75 | 「中匹配」 |
| `low` | < 0.50 | 「低匹配」（**不得展示为高匹配**） |
| 不展示 | < 0.35（`MATCH_MIN_DISPLAY_SCORE`） | 默认过滤 |

阈值全部来自配置，调整需在 [test-report.md](test-report.md) 中记录并说明对指标的影响。

### 3.4 可解释性输出

每个候选必须返回：

| 字段 | 内容 | 生成方式 |
|---|---|---|
| `score_detail` | 六个维度分 | 程序计算 |
| `evidence` | 正向匹配依据（如「物品类别一致」「时间相差约 1 小时 20 分钟」） | 程序按命中的规则生成，可选由 MaaS 润色 |
| `uncertainties` | 不确定因素（如「品牌信息未确认」「两张图片拍摄角度不同」） | 程序识别缺失/冲突项后生成 |
| `risk_tips` | 风险提示（如「耳机属于高仿冒风险类别」） | 程序按类别与分数生成 |

**红线**：`evidence` 不得使用确定性措辞（禁止「确认」「就是」「所有权」等）。

## 4. 属性提取

### 4.1 输出结构（必须通过 Schema 校验）

```json
{
  "category": "无线耳机",
  "brand": null,
  "model": null,
  "color": "黑色",
  "material": null,
  "visible_features": ["椭圆形充电盒", "盒体右侧疑似有划痕"],
  "accessories": ["左右耳机", "充电盒"],
  "keywords": ["蓝牙耳机", "黑色", "无线"],
  "uncertainties": ["品牌标识不清晰"]
}
```

### 4.2 两条实现路径

| 路径 | 触发条件 | 说明 |
|---|---|---|
| **MaaS 模型** | `MAAS_ENABLED=true` 且调用成功 | 提示词版本 `v1.2`，温度 0.1（提高可复现性） |
| **规则实现**（降级） | MaaS 未启用 / 超时 / 返回非法 JSON | 基于 `matching.yaml` 的词表：类别关键词、品牌表、颜色表、材质表、特征正则、配件表 |

**降级是强制要求**：AI 失败**绝不能**导致发布失败，物品仍需成功创建，`ai_status=failed`，
允许用户手动填写属性。

### 4.3 强制约束

1. AI 输出必须经过 JSON Schema 校验；
2. 保留不确定性 —— 出现「疑似 / 好像 / 大概 / 可能 / 记不清」等标记词的属性只作为推测，写入 `uncertainties`；
3. **不得把 AI 结果表述为确定事实**；
4. 记录模型名称、提示词版本、分析时间（`ai_model_version` / `ai_prompt_version` / `ai_analyzed_at`），便于复现与答辩说明；
5. 用户修改后的属性优先级高于 AI 自动属性（`items.attributes_edited_by_user = 1`）；
6. 不得提取或推测任何个人身份信息。

## 5. 可信度评估

### 5.1 公式（冻结，需求 §4.5.3）

```text
可信度分 = 0.60 × 隐藏特征答案匹配
         + 0.20 × 候选物品综合匹配分
         + 0.10 × 发布信息完整度
         + 0.10 × 行为/风险规则分
```

| 风险等级 | 可信度区间 |
|---|---|
| `low` | ≥ 0.75 |
| `medium` | 0.45 ~ 0.75 |
| `high` | < 0.45 |

> ⚠ **不要把两个同名的「阈值」混淆**（这是实现中最容易出错的地方）：
>
> | 配置项 | 含义 | 值 |
> |---|---|---|
> | `questions.yaml → scoring.risk_levels` | 整份认领申请的风险等级 | **0.75 / 0.45**（与契约 §2.6 一致） |
> | `questions.yaml → answer_matching.fuzzy.confident_threshold` | 单道题的答案相似度算不算命中 | 0.50（与上者无关） |
> | `matching.yaml` 的匹配等级 | 候选匹配等级（`match_level`） | 0.75 / 0.50 |
>
> 有单元测试（`TestRiskThresholdsAlignWithContract`）守护第一行与契约的一致性。

### 5.1.1 低答案匹配必须拉高风险（防冒领关键规则）

「隐藏特征几乎全部答错」是最典型的冒领信号。但按公式计算，即使答案分接近 0，可信度也会因为
匹配分、完整度、行为分的存在而落在 0.45 附近，**可能被判为 medium 而非 high**。因此必须有一条
风险规则把它压下：

```yaml
# questions.yaml → behavior.rules
- id: very_low_answer_match
  penalty: 0.35
  tip: "隐藏特征回答与登记信息几乎不吻合，冒领风险高，必须线下核验"
  condition: answer_match_score_lt   # ⚠ 必须写完整信号名 + 比较后缀
  threshold: 0.30
```

**两个实现要点（踩过的坑，勿重蹈）**

1. 信号名必须是 `answer_match_score`（由 `credibility.py` 在评分时自动注入为规则信号）；
   **不能简写为 `answer_match_lt`** —— 规则引擎按后缀剥离得到信号名，简写会去查不存在的
   `answer_match` 信号，规则**永不触发且不报错**。
2. 只有「确实评判过题目」时才注入该信号。没有任何题目时答案分是本项**中性分 0.50**，
   属于「无信号」而非「答得差」，**不得据此触发冒领规则**。

**实测效果**

| 场景 | 答案匹配分 | 行为分 | 可信度 | 风险等级 |
|---|---:|---:|---:|---|
| 全部答对 | 1.00 | 1.00 | 0.98 | low |
| 部分答对 | 0.30 | 1.00 | 0.56 | medium |
| **全部答错** | **0.15** | **0.65** | **0.44** | **high** |

> **可信度只是辅助审核依据，不得作为自动确权结论。** 验证通过后状态只能进入
> `pending_review`，`claimed` 只能由管理员审核产生。

### 5.2 答案匹配策略

| 类型 | 策略 | 示例 |
|---|---|---|
| 语义类（外观痕迹、磨损、内部内容） | 同义容忍 + 关键词重叠 | 「划痕」≈「刮痕」；「右侧」≈「右边」 |
| 关键字段（设备名称、编号） | 规范化后精确匹配 | `YiQi-AirPods` = `yiqi airpods` = `ＹｉＱｉ－ＡｉｒＰｏｄｓ` |

**规范化规则**：去首尾空白 → 全角转半角 → 统一小写 → 去除空白与连接符。

### 5.3 答案处理红线（需求 §4.5.4）

1. 标准答案**不得返回前端**；
2. 标准答案**不得写入普通日志**；
3. 只保存**加盐哈希**（`claims.answers_hash`，HMAC-SHA256，盐由 `APP_SECRET_KEY` 派生），
   `answers_plain` 字段预留但 Baseline **默认 NULL 不启用**；
4. `answer_summary` 中的 `reason` 文案**不得回显答案原文**（只能写「关键特征吻合」这类结论）；
5. 语义匹配所需的原文只在 Redis 认领会话中短期持有（TTL 30 分钟），过期即清理；
6. 验证失败允许重新提交，但**限制次数**（默认 3 次）；
7. 连续失败增加风险标记并通知管理员（写 `claim.verify_failed` 审计日志）。

### 5.4 验证问题生成

```text
优先：MaaS 生成（提示词版本 v1.0，明确要求"不得包含答案本身或任何片段"）
   ↓ 失败或校验不通过
回退：algorithm/config/questions.yaml 模板库（按隐藏特征类型匹配）
```

**强制程序化安全校验**（`validate_questions`），任一项不通过即回退模板：

| # | 校验项 | 判定 |
|---|---|---|
| 1 | 题目非空 | 长度 ≥ 5 字 |
| 2 | **不含答案原文或其 ≥4 字连续子串** | 逐特征比对 |
| 3 | 不是是非问 | 不含「是不是」「有没有」「对不对」「是否」 |
| 4 | 问题之间不重复 | 相似度去重 |
| 5 | 不含敏感词 | 词表过滤 |
| 6 | 不询问个人身份信息 | 词表过滤 |
| 7 | 每题对应一个不同的隐藏特征 | `feature_ref` 去重 |

## 6. 配置化要求

**所有权重、阈值、规则词表只有一个来源**：`algorithm/config/`。

| 文件 | 内容 |
|---|---|
| `matching.yaml` | 六维权重、中性分、类别别名与族关系、文本子项权重与校准表、时间分段、地点/品牌规则、颜色材质品牌词表、特征正则、配件表、关键词规则 |
| `locations.yaml` | 虚构校园的地点层级表（≥2 校区、建筑、楼层、相邻关系） |
| `questions.yaml` | 验证问题模板库（按隐藏特征类型） |

**强制要求**

1. 代码中**不得**出现权重数字（如 `0.20`、`0.25`）；
2. 配置文件不可读或字段缺失时，`config_loader` 回退到内置默认值（数值与配置文件一致）并记录警告，**绝不抛异常中断服务**；
3. 后端 `backend/app/core/config.py` 的 `MATCH_WEIGHT_*` 是**兜底默认值**，与 `matching.yaml` 保持一致（有自检脚本 `scripts/verify_m0.py` 校验）；
4. 权重变更必须同步更新本文件 §3.1 与 [test-report.md](test-report.md) 的消融记录。

## 7. 降级与容错

| 失败场景 | 算法服务行为 | 后端行为 | 用户可见 |
|---|---|---|---|
| 算法服务不可达 / 超时 | — | 降级为本地规则匹配，`degraded=true` | 页面橙色条「当前为规则匹配降级结果」 |
| MaaS 不可用 | 走规则提取 | `ai_status=failed` | 提示可手动补充属性，**发布成功** |
| 图像模型不可用 | 走文本兜底向量 | 在 `uncertainties` 标注 | 无感知，图像分参考价值下降 |
| 时间/地点信息缺失 | 返回中性分，不抛异常 | 在 `uncertainties` 标注 | 显示「时间/地点信息不完整」 |
| 配置文件损坏 | 使用内置默认值 + 警告 | 无感知 | 无感知 |

**超时约定**：算法服务默认 30 秒（`ALGORITHM_TIMEOUT`），超时后返回可理解错误并允许重试。

## 8. 真实模型接入指引

**接入原则**：只改配置与实现类，**不改契约**。Mock 与真实实现使用完全相同的 JSON 契约。

### 8.1 接入图像向量模型

```python
# algorithm/app/matcher.py
from app.matcher import register_image_embedder

class MaaSImageEmbedder:
    """华为云 MaaS 多模态模型向量提取。"""
    def embed(self, image_ref: str) -> list[float]:
        # 1) 通过签名 URL 获取图片
        # 2) 调用 MaaS 视觉接口获取 embedding
        # 3) 返回定长 float 列表（维度需与配置一致）
        ...

register_image_embedder("huawei_maas", MaaSImageEmbedder())
```

然后在 `config/matching.yaml` 中改一行：

```yaml
rules:
  image:
    backend: "huawei_maas"    # 从 "mock" 改为真实后端
```

**无需修改任何业务代码、无需改契约、无需前端改动。**

### 8.2 接入真实属性提取模型

1. 在 `backend/app/clients/maas_client.py` 中把 `MAAS_ENABLED` 置为 `true` 并配置 Endpoint / Key / Model；
2. 提示词变更时**必须升级 `PROMPT_VERSION_ATTRIBUTES`**，写入 `items.ai_prompt_version`；
3. 保持 JSON Schema 不变；模型输出经 `_parse_json_safely` 容错解析（支持代码块包裹）；
4. 失败路径保持：返回 `None` → 后端回退规则提取 → `ai_status=failed`。

### 8.3 接入向量数据库

当前 Baseline 由后端做结构化过滤后把候选集传给算法服务。若候选规模增大：

1. 在 `items` 表增加向量列或引入独立向量库；
2. 把召回阶段下推到向量检索（`idx_items_match_pool` 仍保留作结构化过滤）；
3. 算法服务契约不变（仍是「给候选打分」），只把 `candidate_items` 的来源换成向量召回结果。

## 9. 评估与消融

### 9.1 指标（需求 §9.3）

| 指标 | 定义 |
|---|---|
| Recall@1 / Recall@5 | 正样本中正确答案出现在前 1 / 前 5 的比例 |
| Precision@1 | Top-1 结果中真正为正样本的比例 |
| MRR | 平均倒数排名 |
| 正负样本区分准确率 | 正样本总分高于负样本的比例 |
| 可信认领验证准确率 | 验证结论与人工判断一致的比例 |
| 误通过率 | 错误答案被判为通过的比例（**越低越好**） |
| 误拒绝率 | 正确答案被判为不通过的比例 |
| 平均响应时间 | 单次匹配接口耗时 |

**指标必须说明**：数据集规模、样本定义、阈值、模型版本、测试日期。

### 9.2 消融实验（需求 §9.4）

| 实验 | 使用因素 | 目的 |
|---|---|---|
| A | 仅类别 / 关键词 | 基线（模拟传统关键词检索） |
| B | 类别 + 文本属性 | 验证文本属性的增量 |
| C | 类别 + 文本 + 时间地点 | 验证时空信息的增量 |
| D | 图文 + 时间地点 + 类别 + 属性（完整模型） | 验证多源融合的整体效果 |

**目的**：证明多源融合比单一关键词检索有效。实验结果填写于 [test-report.md](test-report.md) §8。

### 9.3 数据集

| 项 | 数值 |
|---|---|
| 物品记录 | 120 条（lost 60 / found 60） |
| 正匹配样本 | 24 组 |
| 负匹配样本 | 36 组（其中 hard_negative 12 组） |
| 类别覆盖 | 无线耳机 / 水杯 / 书籍 / 校园卡 / 雨伞 / 背包 |
| 数据来源 | 全部为人工构造的**确定性合成数据**，无随机、可重复生成 |
| 隐私 | 校园卡/证件类为虚构信息；不含任何真实个人信息 |

**hard_negative 的意义**：同类别同颜色但品牌/细节不同（如都是黑色耳机，但一方 Apple 一方华为），
用于验证模型不会仅凭「类别 + 颜色」就给高分。
